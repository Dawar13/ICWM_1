## SIGReg diff

LeWM (LW module.py L10-36; SWM stable_worldmodel/wm/loss.py L6-38 is identical). It is a copy of LeJEPA's `MINIMAL.md` SIGReg (LJ MINIMAL.md L57-75), with the hard-coded 256 directions made a parameter.

```python
t = torch.linspace(0, 3, knots)                 # knots = 17
dt = 3 / (knots - 1)
weights = torch.full((knots,), 2 * dt); weights[[0, -1]] = dt
window = torch.exp(-t.square() / 2.0)           # phi, the N(0,1) CF on t >= 0
weights = weights * window
# forward(proj), proj: (T, B, D)
A = torch.randn(D, num_proj); A = A / A.norm(dim=0)      # num_proj = 1024
x_t = (proj @ A).unsqueeze(-1) * t                       # (T, B, M, K)
err = (x_t.cos().mean(-3) - phi).square() + x_t.sin().mean(-3).square()   # mean over B
statistic = (err @ weights) * B                          # (T, M)
return statistic.mean()                                  # over directions and time
# used as: loss = pred_loss + 0.09 * sigreg(emb.transpose(0, 1))   (LW train.py L39-41)
```

Ours (model.py L98-112; train.py L205-208):

```python
u = randn(d, 256); u = u / u.norm(dim=0)
x = z.float() @ u                               # z = encoder latents of all h+1 frames, flattened: N = B(h+1)
t = linspace(-5, 5, 17); xt = x[..., None] * t
err = ((cos(xt).mean(0) - exp(-t^2/2))^2 + sin(xt).mean(0)^2) * exp(-t^2/2)
return trapz(err, t).mean() * N
# used as: loss = sum_d (pred - target)^2 .mean() + sigreg_w * sigreg(...)
```

Every difference:

1. **Number of directions:** 1024 (LW config/train/lewm.yaml L43) vs 256. This only changes the variance of the estimate. (paper: the number of directions has little effect.)
2. **t grid and range:** 17 knots on [0, 3] with doubled trapezoid weights (equal to [-3, 3] by symmetry, spacing 0.1875) vs 17 points on [-5, 5] with `torch.trapz` (spacing 0.625). LJ MINIMAL.md L54 says the [0, t_max]-and-double form replaced the paper's [-t_max, t_max] integral; ours is the paper-style form. My own numerical check of the population integrals (not repository code) gives ours/LeWM ratios of 1.003 for N(0, 0.5^2), 1.022 for N(0, 2^2), 1.017 for a point mass (collapse), 1.000 for N(1, 1) and 1.063 for Rademacher. This difference is negligible.
3. **Weighting:** identical. Both use the squared ECF error against `exp(-t^2/2)`, weighted by `exp(-t^2/2)`.
4. **Scaling by N:** LeWM multiplies by B per time step; ours multiplies by N = B(h+1). For the same distribution, ours is (h+1) times larger.
5. **Averaging and pooling:** LeWM tests each time index separately (T = 4 frames: 3 history and 1 target) and averages over time and directions. Ours pools all h+1 frames into one sample and averages over directions only. Clip starts are uniform, so the per-position marginals are similar, and the main effect is item 4. Pooled frames from one clip are correlated, though, so our "N" overstates the number of independent samples.
6. **Tensor:** LeWM uses the projector output `emb` of every frame in the clip, before the predictor, with BN only in the projector's hidden layer. Ours uses the encoder output after an output BatchNorm1d, so each axis is already batch-standardised; SIGReg then mainly acts on correlations between directions and on higher moments.
7. **Weight and the reduction of the prediction loss:** LeWM uses lambda = 0.09 (code; 0.1 in the paper) with a per-element mean squared error. Ours uses `sigreg_w` = 0.1 with a squared error summed over d. Dividing our loss by d gives an equivalent LeWM lambda of `sigreg_w * (h+1) / d`: 0.00625 (d=32, h=1), 0.0125 (d=32, h=3 or d=16, h=1) and 0.025 (d=16, h=3). That is 14, 7.2 and 3.6 times weaker than 0.09. To match LeWM, set `sigreg_w = 0.09 * d / (h+1)`: 1.44, 0.72, 0.72 and 0.36 for those cases. (paper: success stays above 80 % for lambda from 0.01 to 0.2.)
8. **No (1 - lambda):** LeJEPA's minimal code uses `(1 - lamb) * inv + lamb * sigreg` (LJ MINIMAL.md L174). LeWM uses `pred + lambda * sigreg` (LW train.py L41), and so do we.
9. **Randomness and precision:** both draw fresh Gaussian directions on every call and normalise the columns. LeWM trains with Lightning bf16 precision (LW lewm.yaml L21). Ours calls `.float()`, but inside `torch.autocast(bfloat16)` (train.py L192) the matmul still runs in bf16. This is not a material difference.

Verdict: `sigreg_epps_pulley` has the correct functional form (the same statistic, weighting and per-sample N scaling convention), with a different grid and fewer directions. The mismatches that matter are the time pooling (factor h+1) and our summed prediction loss (factor d). Together they make our default weight 3.6 to 14 times weaker than LeWM's.

## Checkpoint loading for G3

Files per HF model repo: `config.json` and `weights.pt` (a `state_dict`), plus `README.md` and `.gitattributes` (HF API sibling list). The configs are identical across environments except `action_encoder.input_dim`: 10 for pusht, tworooms and reacher; 25 for cube. Every config has `predictor.num_frames: 3`.

Route A, stable-worldmodel (SWM stable_worldmodel/wm/utils.py L50-96, HF resolution L144-163):
`from stable_worldmodel.wm.utils import load_pretrained; model = load_pretrained("quentinll/lewm-pusht")`. This downloads `config.json` and `weights.pt` into `<STABLEWM_HOME>/checkpoints/models--quentinll--lewm-pusht/`, calls `hydra.utils.instantiate(config)` to build `stable_worldmodel.wm.lewm.LeWM`, then `load_state_dict` (default strict). The encoder is `stable_pretraining.backbone.utils.vit_hf(size="tiny", patch_size=14, image_size=224, pretrained=False, use_mask_token=False)`; its internals were not read.

Route B, le-wm README (LW README.md L137-181): build `jepa.JEPA(encoder=vit_hf(...), predictor=ARPredictor(**cfg["predictor"]), action_encoder=Embedder(**cfg["action_encoder"]), projector=MLP(..., norm_fn=BatchNorm1d), pred_proj=MLP(...))`, then `torch.load("weights.pt")` and `load_state_dict(sd, strict=True)`.

Inputs and calls (LW jepa.py L29-55; SWM lewm.py L24-51):
- `pixels`: (B, T, 3, 224, 224) float, converted with ImageNet mean and std and resized to 224 (LW utils.py L6-10; eval.py L17-26). The encoder is called with `interpolate_pos_encoding=True`, and the CLS token is used.
- `action`: (B, T, 5 * action_dim), that is (B, T, 10), or (B, T, 25) for cube. Each block is the 5 raw actions leaving that frame. Z-score the raw per-step actions per dimension with dataset statistics, then group them (row "Action encoder" above). The normaliser statistics are not stored in the checkpoint: recompute them from the dataset's `action` column, as eval.py L71-79 does with `StandardScaler`. Replace NaN with 0.
- `info = model.encode({"pixels": px, "action": act})` gives `info["emb"]` (B, T, 192) and `info["act_emb"]` (B, T, 192). Then `pred = model.predict(info["emb"][:, :3], info["act_emb"][:, :3])` gives (B, 3, 192), where `pred[:, k]` predicts the embedding of frame k+1 from frames 0..k and action blocks 0..k (causal mask).
- Call `model.eval()` first: the projector and `pred_proj` contain BatchNorm1d, and the predictor has dropout 0.1.
- For the truncated-history CAS: feeding T = 1 uses `pos_embedding[:, :1]` and is exactly the computation that position 0 was trained on, so a history-1 prediction is in distribution. Replacing the history with copies of the latest latent at positions 0..2 is not a configuration seen in training. Pre-register which one G3 uses.
- Data: `tar --zstd -xvf` the HF archives and place the `.h5` files under `$STABLEWM_HOME` (LW README.md L39-52). Load them with `swm.data.HDF5Dataset` (LW eval.py L40-47) or with `swm.data.load_dataset(name, num_steps=4, frameskip=5, keys_to_load=[...])` (LW train.py L53-58). The PushT training configs name `pusht_expert_train.lance` (LW config/train/data/pusht.yaml L4), while the README speaks of `.h5`; check what the HF PushT archive contains.
- Dependencies: `stable_worldmodel`, `stable_pretraining`, `hydra`, `einops` and, for Route B, the le-wm source files `jepa.py` and `module.py`.

## Inconsistencies to keep in mind

- lambda: 0.09 in code vs 0.1 in the paper. Which value produced the HF checkpoints is not determinable from code, because `config.json` stores only the model.
- Epochs: 100 in code vs 10 in the paper.
- TwoRoom history: 3 in code and in the HF config vs 1 in the paper. If the HF TwoRoom weights load strictly with `num_frames: 3`, the checkpoint was built with history 3 (not verified; nothing downloaded).
- Reacher data: a random policy in the SWM collection script and the `reacher_random` eval name vs a SAC policy in the paper.
- TwoRoom `action_repeat_prob=0.05` is dead code at SWM `21446f1`.
